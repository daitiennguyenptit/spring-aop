1. Mục đích của Spring AOP

AOP (Aspect-Oriented Programming) giải quyết các cross-cutting concern, tức những mối quan tâm "cắt ngang" nhiều tầng và nhiều class nhưng không thuộc nghiệp vụ chính: ghi log, audit, đo thời gian, phân quyền, transaction, retry, cache…

Nếu không có AOP, các đoạn code này gây ra hai vấn đề:

  • Code tangling (rối): trong một method, logic nghiệp vụ bị trộn lẫn với log, đo thời gian, kiểm quyền.
  • Code scattering (rải rác): cùng một đoạn code log/audit bị lặp lại ở hàng trăm method. Khi cần sửa format thì phải sửa ở hàng trăm chỗ, và rất dễ sót.
Không dùng AOP
public String transfer(String requestId, String from,
                       String to, BigDecimal amount) {
    long start = System.nanoTime();
    if (!user.hasRole("TELLER")) throw ...;
    log.info("[{}] TRANSFER start {}", requestId, from);
    try {
        accountService.debit(requestId, from, amount);
        accountService.credit(requestId, to, amount);
        auditRepo.save(requestId, "TRANSFER", "OK");
        return "OK";
    } catch (Exception e) {
        auditRepo.save(requestId, "TRANSFER", "FAIL");
        throw e;
    } finally {
        metrics.record(System.nanoTime() - start);
    }
}
Dùng AOP
@RequiresRole("TELLER")
@Audited(action = "TRANSFER")
public String transfer(String from, String to,
                       BigDecimal amount) {
    accountService.debit(from, amount);
    accountService.credit(to, amount);
    return "OK";
}
// Log, audit, metrics, phân quyền nằm trong
// các Aspect riêng, viết MỘT lần và áp dụng
// cho mọi method bằng annotation/pointcut.
// requestId không còn trong tham số.
Tóm lạiAOP giúp tách "làm gì" (nghiệp vụ) khỏi "làm thế nào cho an toàn và quan sát được" (hạ tầng). Code nghiệp vụ gọn hơn, concern được quản lý tập trung, dễ bật/tắt và dễ test.

Thật ra bạn đã dùng Spring AOP hằng ngày mà không để ý: @Transactional, @Cacheable, @Async, @PreAuthorize, @Retryable đều được cài đặt bằng proxy AOP.

3. Cơ chế hoạt động: Proxy

Khi khởi động, một BeanPostProcessor (AnnotationAwareAspectJAutoProxyCreator) duyệt qua từng bean. Thứ tự trong cùng một aspect (Spring ≥ 5.2.7), đã được kiểm chứng bằng test:

Thành công: around-before → before → [method] → afterReturning → after → around-after
Có lỗi:     around-before → before → [method] → afterThrowing  → after → around-after

Demo: 01-aop-basics/…/aspect/TracingAspect.java

@Around("com.example.aop.basics.aspect.Pointcuts.placeOrder()")
public Object around(ProceedingJoinPoint pjp) throws Throwable {
    trace.add("around-before");
    try {
        return pjp.proceed();          // gọi tiếp chuỗi advice / target
    } finally {
        trace.add("around-after");
    }
}

@AfterReturning(pointcut = "...placeOrder()", returning = "result")
public void afterReturning(Object result) { trace.add("afterReturning:" + result); }
Quy tắc chọn adviceHãy chọn loại advice "yếu" nhất đủ dùng. @Around mạnh nhất nhưng dễ gây lỗi: quên return pjp.proceed() thì method trả về null, còn nuốt exception thì làm hỏng luồng nghiệp vụ.

6.1 Bài toán trọng tâm: ghi audit log cho từng hàm, có requestId, không cần truyền vào tham số

Đề bài

Hệ thống ngân hàng yêu cầu mọi thao tác nghiệp vụ (xem số dư, ghi nợ, ghi có, chuyển tiền, gửi thông báo) phải có bản ghi audit gồm: requestId, hành động, method, tham số (đã che dữ liệu nhạy cảm), kết quả hoặc lỗi, thời gian xử lý, thread. Mọi bản ghi sinh ra từ cùng một request phải có cùng requestId, để khi khách hàng khiếu nại thì tra được toàn bộ chuỗi thao tác.

Cách làm "ngây thơ" và vì sao nó tệThêm tham số String requestId vào mọi method rồi truyền tay từ Controller xuống Service, Repository, Client. Kết quả là chữ ký hàm bị ô nhiễm bởi hạ tầng, phải sửa hàng trăm method, dễ truyền sai hoặc quên, và thư viện bên thứ ba không thể nhận thêm tham số. Thêm vào đó, code audit vẫn bị lặp ở mọi hàm.

Ý tưởng giải pháp

  1. Một điểm vào duy nhất (RequestIdFilter) nhận header X-Request-Id từ gateway hoặc tự sinh UUID, sau đó lưu vào ThreadLocal và MDC.
  2. Context gắn với thread (RequestContext): ở bất kỳ tầng nào, chỉ cần gọi RequestContext.getRequestId(). Vì Servlet xử lý mỗi request trên một thread, giá trị này "đi theo" request mà không cần truyền.
  3. Annotation khai báo (@Audited(action = "...")) đánh dấu hàm cần audit, kèm @Sensitive trên tham số nhạy cảm.
  4. Aspect @Around (AuditAspect) đọc requestId từ context, đo thời gian, ghi bản ghi SUCCESS hoặc FAILURE, rồi ném lại exception.
  5. Truyền context sang thread khác (TaskDecorator) để @Async vẫn giữ đúng requestId.
  6. Dọn dẹp trong finally, vì thread của Tomcat được tái sử dụng. Quên bước này thì requestId sẽ rò sang request khác.

Bước 1: Context theo thread

02-audit-requestid/src/main/java/com/example/aop/audit/context/RequestContext.java

public final class RequestContext {
    public static final String REQUEST_ID = "requestId";
    private static final ThreadLocal<String> HOLDER = new ThreadLocal<>();

    public static void setRequestId(String id) { HOLDER.set(id); MDC.put(REQUEST_ID, id); }
    public static String getRequestId()         { return HOLDER.get(); }
    public static void clear()                  { HOLDER.remove(); MDC.remove(REQUEST_ID); }

    // Entry point không phải HTTP (scheduled job, Kafka consumer...)
    public static <T> T callWithRequestId(String id, Supplier<T> action) { ... }
}

Bước 2: Filter là điểm duy nhất tạo requestId

02-audit-requestid/…/web/RequestIdFilter.java

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequestIdFilter extends OncePerRequestFilter {
    public static final String HEADER = "X-Request-Id";
    private static final Pattern SAFE_ID = Pattern.compile("^[A-Za-z0-9._-]{1,64}$");

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) ... {
        String requestId = resolveRequestId(req.getHeader(HEADER));  // validate: chống log injection
        RequestContext.setRequestId(requestId);
        res.setHeader(HEADER, requestId);                            // trả về cho client đối soát
        try {
            chain.doFilter(req, res);
        } finally {
            RequestContext.clear();                                  // BẮT BUỘC
        }
    }
}

Bước 4: Aspect audit

02-audit-requestid/…/aspect/AuditAspect.java

@Aspect @Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
public class AuditAspect {

    @Around("@annotation(audited)")
    public Object audit(ProceedingJoinPoint pjp, Audited audited) throws Throwable {
        MethodSignature sig = (MethodSignature) pjp.getSignature();
        String requestId = currentRequestId();                    // đọc từ ThreadLocal, KHÔNG từ tham số
        String arguments = describeArguments(sig.getMethod(), pjp.getArgs());  // che @Sensitive
        long start = System.nanoTime();
        try {
            Object result = pjp.proceed();
            write(new AuditRecord(requestId, audited.action(), ..., SUCCESS, ...));
            return result;
        } catch (Throwable ex) {
            write(new AuditRecord(requestId, audited.action(), ..., FAILURE, ex.getMessage(), ...));
            throw ex;                                              // không nuốt exception
        }
    }
}

Bước 6: Mang requestId sang thread @Async

ThreadLocal không tự đi sang thread khác. Ta dùng TaskDecorator để chụp context trên thread gọi, rồi khôi phục trên thread worker:

02-audit-requestid/…/config/AsyncConfig.java

@Bean
public TaskDecorator requestContextTaskDecorator() {
    return runnable -> {
        String requestId = RequestContext.getRequestId();          // thread GỌI
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        return () -> {                                            // thread WORKER
            if (mdc != null) MDC.setContextMap(mdc);
            if (requestId != null) RequestContext.setRequestId(requestId);
            try { runnable.run(); } finally { RequestContext.clear(); MDC.clear(); }
        };
    };
}

Lưu ý khi đưa lên production

Bảo mật logValidate header requestId (chống log injection), che PII và dữ liệu thẻ/OTP/mật khẩu bằng @Sensitive hoặc whitelist field, không log nguyên object request.

6.2 Đo hiệu năng và cảnh báo method chậm

Bài toán: cần biết method nào chậm trên production mà không phải chèn System.nanoTime() vào từng hàm. Ngưỡng mặc định lấy từ cấu hình, và có thể ghi đè cho từng method.

Giải pháp: pointcut theo vị trí (mọi bean @Service trong package), không cần annotation. @Monitored chỉ dùng để ghi đè ngưỡng.

03-performance-monitoring/…/aspect/PerformanceAspect.java

@Around("within(@org.springframework.stereotype.Service *) && within(com.example.aop.perf.service..*)")
public Object measure(ProceedingJoinPoint pjp) throws Throwable {
    long start = System.nanoTime();
    try {
        return pjp.proceed();
    } finally {
        long ms = (System.nanoTime() - start) / 1_000_000;
        long threshold = thresholdOf(signature.getMethod());   // @Monitored hoặc perf.slow-threshold-ms
        metrics.record(name, ms, ms >= threshold);
        if (ms >= threshold) log.warn("SLOW method {} took {} ms", name, ms);
    }
}

curl localhost:8083/reports/slow ; curl localhost:8083/metrics/methods

6.3 Retry tự động khi gọi hệ thống ngoài

Bài toán: gọi cổng thanh toán đôi khi bị timeout hoặc 503. Cần retry lỗi tạm thời với backoff tăng dần, nhưng không retry lỗi nghiệp vụ (ví dụ thẻ bị khóa).

Mấu chốt: ProceedingJoinPoint.proceed() có thể gọi nhiều lần.

04-retry/…/aspect/RetryAspect.java

@Around("@annotation(retry)")
public Object retry(ProceedingJoinPoint pjp, RetryOnFailure retry) throws Throwable {
    long backoff = retry.backoffMs();
    for (int attempt = 1; ; attempt++) {
        try {
            return pjp.proceed();
        } catch (Throwable ex) {
            if (!isRetryable(ex, retry) || attempt >= retry.maxAttempts()) throw ex;
            Thread.sleep(backoff);
            backoff *= 2;                                   // exponential backoff
        }
    }
}

@RetryOnFailure(maxAttempts = 3, backoffMs = 50, retryFor = TransientException.class)
public String charge(String paymentId) { ... }
Cảnh báo: idempotencyChỉ retry thao tác idempotent, hoặc có idempotency key (ở đây là paymentId). Nếu retry một lệnh trừ tiền không idempotent, khách hàng có thể bị trừ tiền hai lần.
Thứ tự với @TransactionalRetry phải bọc ngoài transaction (order nhỏ hơn), để mỗi lần thử là một transaction mới. Nếu retry nằm bên trong, transaction đã bị đánh dấu rollback-only và retry trở nên vô nghĩa.

Test: thành công ở lần thứ 3, hết lượt thử thì ném lại lỗi gốc, lỗi nghiệp vụ chỉ thử 1 lần. Trên production, nên cân nhắc Spring Retry (@Retryable) hoặc Resilience4j (có thêm circuit breaker).

6.4 Phân quyền bằng annotation

Bài toán: teller được xem hồ sơ vay, chỉ manager được duyệt, toàn bộ AdminService chỉ dành cho admin. Không muốn viết if (!user.hasRole(..)) ở mọi hàm.

05-authorization/…/aspect/AuthorizationAspect.java

@Before("@annotation(com.example.aop.authz.annotation.RequiresRole) "
      + "|| @within(com.example.aop.authz.annotation.RequiresRole)")
public void checkRole(JoinPoint jp) {
    RequiresRole required = resolveAnnotation(jp);   // ưu tiên method, sau đó tới class
    CurrentUser user = UserContext.get();             // lại là pattern ThreadLocal
    if (user == null) throw new UnauthenticatedException();   // 401
    if (Arrays.stream(required.value()).noneMatch(user.roles()::contains))
        throw new AccessDeniedException(...);                  // 403, method không bao giờ chạy
}

7. Thứ tự khi nhiều aspect cùng áp dụng

Dùng @Order trên class aspect: số nhỏ hơn thì ưu tiên cao hơn, nghĩa là bọc ngoài, chạy trước ở chiều vào và chạy sau ở chiều ra. Gợi ý cho hệ thống nghiệp vụ:

Authorization (+50)  →  Retry (+100)  →  Audit  →  @Transactional (LOWEST_PRECEDENCE)  →  method
     chặn sớm nhất         mỗi lần thử             ghi cả kết quả       transaction trong cùng
                           = 1 transaction mới     commit/rollback

Với @Transactional, có thể đổi order bằng @EnableTransactionManagement(order = ...). Không đặt @Order thì thứ tự giữa các aspect là không xác định.

8. Best practice và khi nào KHÔNG nên dùng AOP

Nên

  • Dùng pointcut theo annotation cho code ứng dụng, để rõ ràng và có chủ đích.
  • Giữ aspect mỏng và nhanh. Việc nặng (ghi DB, gọi mạng) thì làm bất đồng bộ.
  • Luôn return pjp.proceed() và ném lại exception.
  • Đặt @Order rõ ràng khi có nhiều aspect.
  • Dọn ThreadLocal trong finally.
  • Viết test chứng minh aspect thật sự được áp dụng.

Không nên

  • Đặt logic nghiệp vụ vào aspect. Người đọc code sẽ không thấy nó, gây ra "magic".
  • Dùng pointcut quá rộng như execution(* *(..)), vì nó dính cả bean của framework.
  • Thay đổi tham số hoặc kết quả một cách âm thầm trong @Around.
  • Nuốt exception trong aspect audit hoặc log.
  • Dùng AOP cho logic chỉ xuất hiện ở 1–2 chỗ. Khi đó gọi hàm trực tiếp rõ ràng hơn.
